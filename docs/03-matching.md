# 3. Механика подбора и категоризации

## 3.1. Принцип: инициатива у работодателя

На досках вакансий кандидат откликается вслепую, а работодатель вручную фильтрует сотни резюме. В «Драфте» —
наоборот (ориентир — модель LHH):

1. кандидат **один раз** подтверждает уровень и попадает в категорию;
2. работодатель описывает **потребность** и получает подборку из подходящих категорий с объяснением;
3. работодатель **сам приглашает конкретного человека**: описание, вилка (обязательна), компания, способ связи;
4. кандидат видит условия **до начала общения** и принимает или отклоняет приглашение с причиной;
5. контакты кандидата раскрываются **только после принятия** (или после самостоятельного отклика).

Самостоятельный отклик на вакансию сохранён как дополнительный сценарий для кандидатов, которые пока не получили приглашений.

## 3.2. Категоризация

Все зарплаты на платформе — **в месяц, до вычета НДФЛ (gross)**; подпись «gross» стоит у каждой суммы в интерфейсе, письмах
и API. Если в тексте вакансии вилка указана «на руки», разбор переводит её в gross по ставке НДФЛ 13% и сообщает об этом.


**Категория = специализация × грейд**, где оба значения получены из обязательного пути (опрос → выбор грейда → тест), а
не из резюме. Справочник:

* направления (отрасли ИТ): разработка ПО, данные и ИИ, инфраструктура, качество ПО, кибербезопасность;
* 8 специализаций: Backend, Frontend, Mobile, Data Science / ML, аналитика данных, DevOps / SRE, QA, информационная безопасность;
* 4 грейда: стажёр, junior, middle, senior (порог по шкале теста и типичный стаж);
* онтология ~130 навыков с синонимами и связями (используется для нормализации резюме, потребностей и проверки навыков).

Опрос дополнительно фиксирует основной язык/фреймворк (трек заданий), стек, стаж, роль в команде (исполнитель, ментор,
тимлид, техлид), отраслевой опыт (финтех, ритейл, госсектор…) и формат работы — это используется в подборе и объяснении.
Грейд — это **уровень навыков, подтверждённый тестом**; стаж остаётся атрибутом профиля и подсказкой при выборе грейда.

**Несколько категорий у одного кандидата.** Кроме основной категории кандидат может добавить до двух дополнительных
(например, backend-разработчик, который работает и как DevOps). Грейд в каждой подтверждается только своим тестом:
дополнительная категория сначала видна со статусом «не подтверждён» и ниже подтверждённых, как и основная. Тест проходится
по основной категории, поэтому дополнительную можно сделать основной — поля категорий меняются местами, и у каждой
сохраняются свой грейд, результат теста, блокировка смены грейда на 90 дней и паузы на пересдачу. Работодатель находит
кандидата во всех его категориях: в подборке кандидат участвует лучшей из подходящих запросу категорий, в поиске — той,
что совпала с фильтром; в карточке видно, по какой категории он найден, и список остальных («также: DevOps · Junior»).
Навык, подтверждённый тестом в любой категории, считается подтверждённым. Карта категорий учитывает дополнительные
категории в своих ячейках. (`app/services/categories.py`, `POST /candidate/categories`, `POST /candidate/categories/{spec}/main`)

**Внутри категории** кандидаты ранжируются по **силе подтверждённого профиля**:

```
strength = 100 · (0.55·T + 0.20·F + 0.15·A + 0.10·P)
  T — положение θ̂ внутри полосы грейда (результат теста),
  F — сила достижений ФСП (0, если истории нет — штрафа нет, бонуса нет),
  A — актуальность: свежесть активности, решённые регулярные задачи и их оценки,
  P — полнота профиля.
```

Для каждой категории считается перцентиль силы — в выдаче: «сильнее 86% кандидатов категории».

## 3.3. Подборка по потребности: два этапа

### Этап 1 — отбор по категориям (recall)

* **целевые категории**: специализация потребности × выбранные грейды;
* **смежный грейд** (±1 ступень) — с понижающим коэффициентом 0.92 и пометкой («на ступень ниже, близок к повышению»);
* **смежная специализация** (backend ↔ devops/qa, ml ↔ аналитика, frontend ↔ mobile…) — коэффициент 0.85.

Выдача упорядочена по категориям: сначала целевая, затем смежные — так выдача формируется на основании категорий, а не
текстового совпадения. В подборку не попадают скрытые профили и кандидаты со статусом «не ищу».

**Грейд не подтверждён.** Кандидат, который прошёл опрос и заявил грейд, но ещё не подтвердил его тестом (или не прошёл
тест), **не скрывается**, как рекомендовали постановщики: он показывается в категории заявленного грейда со статусом
«грейд не подтверждён тестом» и **после всех подтверждённых** кандидатов. Компонента уровня L для него равна 0, итоговая
оценка умножается на 0.6, в объяснении — предупреждение. Работодатель может включить фильтр «только с подтверждённым
грейдом», на карте категорий такие кандидаты показаны отдельным числом. Так кандидат не выпадает из оборота, а выдача
по-прежнему строится на категориях, подтверждённых тестом.

### Этап 2 — ранжирование (precision) с объяснимостью

Интерпретируемая взвешенная сумма шести компонент, каждая в [0, 1]:

| Компонента | Вес (экспертный → подобранный) | Как считается |
|---|---|---|
| **L** подтверждённый уровень | 0.30 → **0.39** | целевая категория: 0.55 + 0.45·(положение θ̂ в полосе грейда); смежный грейд ниже: 0.2 + 0.35·положение; выше: 0.5 |
| **S** навыки | 0.30 → **0.20** | покрытие обязательных (80%) и желательных (20%) навыков с учётом **силы доказательства** |
| **F** достижения ФСП | 0.20 → **0.12** × (0.2…1.0) | оценка достижений с учётом **актуальности дисциплины для запроса** (профильная 1.0, смежная 0.8, непрофильная 0.6; стек решения совпал с навыками запроса — профильная, п. 5.3); долю (20–100% от максимума) задаёт работодатель ползунком «важность ФСП» |
| **C** условия | 0.15 → **0.15** | 0.7·соответствие ожиданий вилке + 0.3·формат и город |
| **A** актуальность | 0.08 → **0.05** | свежесть активности, регулярные задачи |
| **D** контекст | 0.07 → **0.08** | отраслевой опыт + TF-IDF-близость описания потребности и профиля |

Веса нормируются к 1. Затем применяются **гейт** и множители:

```
score = 100 · Σ wᵢ·компонентаᵢ × (g + (1 − g)·покрытие_обязательных),  g = 0.26 (было 0.50)
        × 0.62, если ожидания выше вилки более чем на 10%   (было 0.85)
        × 0.68, если формат работы несовместим            (было 0.85)
        × 0.90 / 0.88 для смежного грейда / специализации    (было 0.92 / 0.85)
        × 0.60, если грейд заявлен, но не подтверждён тестом
```

**Как подобраны веса.** Экспертные значения были стартовой точкой. Затем веса и множители подобраны случайным поиском
с покоординатным уточнением на **отдельных** наборах потребностей (`python -m app.validation.tune_matching`, результат —
`app/matching/tuned_params.json`), а качество измеряется на других, независимых наборах (п. 4): nDCG@10 0.772 → 0.793,
P@5 0.828 → 0.848. Подбор идёт **в продуктовых рамках**: навыки ≥ 20%, ФСП ≥ 10%, уровень 20–40%, текст резюме ≤ 12%.
Без рамок поиск увеличивал вес текста резюме и обнулял подтверждённые навыки и ФСП — это подгонка под синтетику,
противоречащая ТЗ (выдача по подтверждённому профилю, ФСП поднимает кандидата). Экспертные веса доступны для сравнения
(`EXPERT_PARAMS`), а одна функция `combine()` считает оценку в продакшене, валидации и подстройке.

Гейт по обязательным навыкам не даёт высокому грейду и хорошим условиям вытянуть наверх человека без нужного стека.

### Сила доказательства навыка

| Источник | Вес | Когда |
|---|---|---|
| Тест | 1.0 × доверие | навык заявлен (или это язык/фреймворк из опроса) и подтверждён сильным результатом по соответствующей компетенции; смежные навыки — с коэффициентом (PostgreSQL через «Базы данных» — 0.85, Kafka через «Архитектуру» — 0.6) |
| ФСП | 0.9 | навык использован на соревновании (стек результата в реестре ФСП) или прямо проверяется дисциплиной (CTF → веб-безопасность) |
| Регулярная задача | 0.8 | навык задачи работодателя, решённой на 4–5 |
| Резюме | 0.5 | навык только заявлен |
| Смежный навык | 0.3–0.35 | есть связанный навык (MySQL при запросе PostgreSQL) или сильная смежная компетенция без заявления навыка |

### Объяснение выдачи

Каждая компонента возвращает человекочитаемые причины и предупреждения. В карточке кандидата работодатель видит:

* вклад каждой компоненты (полосы и «+29 / +26 / +2.8…»);
* навыки запроса с типом доказательства: **тест**, **ФСП**, **задача**, **резюме**, **смежный**, **нет**;
* причины («Категория Backend · Middle подтверждена адаптивным тестом, 86-й перцентиль», «Подтверждены тестом: Python, SQL»,
  «ФСП: Призёр — Чемпионат СЗФО по продуктовому программированию 2026», «Ожидания 250–300 тыс. ₽ укладываются в вилку»);
* предупреждения («Нет подтверждения обязательных навыков: Kafka», «Ожидания выше вилки на 15%», «Смежная категория…»);
* **вероятность принятия приглашения** (логистическая модель: статус поиска, соответствие вилки, формат, свежесть активности,
  число висящих приглашений) — помогает выбрать, кому писать, и реалистично назначить вилку.

### Сравнение кандидатов «почему A выше B»

В подборке можно выбрать 2–3 кандидатов и открыть сравнение (`GET /employer/needs/{id}/compare`): рядом — итоговая оценка,
вклад каждой из шести компонент, навыки запроса с типом доказательства, ожидания относительно вилки, ФСП и вероятность
принятия. Для соседей по рейтингу система объясняет разрыв: какие компоненты дали первому больше баллов, в чём сильнее
второй и какие множители сработали («ожидания выше бюджета (×0.62)», «покрыто 67% обязательных навыков»). Сравнение
считается той же формулой, что и подборка.

### Рекомендованные категории

Над списком — карточки категорий: целевые и смежные, число кандидатов, сколько с достижениями ФСП, доля кандидатов, чьи
ожидания укладываются в вилку, медианные ожидания («медианные ожидания 440 тыс. ₽ выше вашей вилки»). Клик по карточке
уточняет подборку до этой категории.

## 3.4. Уточнение без потери подборки

Подборка сохраняется на сервере (`shortlist_entries`: ранг, оценка, объяснение, пометка). Фильтры (грейд, «обязательно
владеет», «только подтверждённые», ФСП, «в моей вилке», формат, минимальное соответствие, отношение к категории)
применяются **поверх** сохранённой подборки — счётчик показывает «показано 12 из 60, исходная подборка сохранена», сброс
уточнений возвращает всё. Пометки «избранное» и «скрыт» сохраняются при пересчёте подборки («Обновить подборку»), а кандидат,
выпавший из категории, остаётся в избранном.

## 3.5. Приглашение и его жизненный цикл

Приглашение содержит описание предложения, вилку «от–до» в рублях (обязательно), название компании, способ связи, формат,
срок ответа и (необязательно) ссылку на потребность или вакансию.

```
sent ──(кандидат открыл)──▶ viewed ──▶ accepted ──▶ этапы: contact → interview → offer → hired | closed
  │                           │
  │                           └──▶ declined (причина: зарплата, формат, сфера, стек, не ищу, компания, другое)
  ├──(истёк срок)──▶ expired
  └──(работодатель)──▶ withdrawn
```

* Обе стороны видят актуальный статус и этап своих записей; каждое событие — уведомление (в приложении и по e-mail).
* При принятии контакты раскрываются работодателю, событие пишется в аудит и отправляется вебхуком в ATS.
* Причины отказов агрегируются в аналитике работодателя («40% отказов — зарплата ниже ожиданий»).
* Массовое приглашение — до 50 кандидатов одним действием, с лимитами по индексу доверия (п. 10).

## 3.6. Правила видимости

| Данные | До принятия / отклика | После |
|---|---|---|
| Категория, θ-перцентиль, профиль компетенций, подтверждённые навыки | видны | видны |
| Достижения ФСП, результаты задач, ожидания по зарплате | видны, если кандидат не скрыл | видны |
| Имя | по умолчанию **код кандидата** (снижение предвзятости), кандидат может открыть | видно |
| Места работы из опыта | видны; текущий работодатель скрыт по умолчанию (чтобы его не узнал нынешний наниматель), кандидат может открыть | видны |
| E-mail, телефон, Telegram, GitHub | **скрыты** | видны работодателю, которому кандидат ответил |

Кандидат видит только свои приглашения и отклики; работодатель — только свои потребности, приглашения, вакансии и задачи
(проверено автотестами).

ТЗ закрывает до принятия приглашения только контактные данные; организаторы подтвердили, что ФИО и места работы показывать
допустимо. «Драфт» делает это выбором кандидата: по умолчанию работодатель видит код и опыт без текущего места работы
(слепой первичный отбор и минимизация персональных данных по 152-ФЗ), а кандидат одним переключателем открывает имя
и текущую компанию.
