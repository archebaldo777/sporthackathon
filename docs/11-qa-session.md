# 11. Соответствие решениям сессии вопросов и ответов

На сессии вопросов и ответов постановщики (ментор, юрисконсульт ФСП, эксперт по веб-платформам, продуктовый специалист
ФСП) уточнили требования. Ниже — каждое решение и то, как оно реализовано в «Драфте».

## 11.1. Тест, грейд, категория

| Решение на сессии | Как в «Драфте» | Где |
|---|---|---|
| Грейд — только по первичному тесту категории, не по вакансии и не по достижениям ФСП | Грейд меняет только завершённая попытка теста по специализации. ФСП, резюме и вакансия на грейд не влияют: итоговая θ оценивается с популяционным априорным распределением, ФСП в тест не входит | `testing/service.py: finish_attempt`, п. 2.4 |
| Достижения ФСП — ранжирование внутри категории | Компонента F силы профиля и формулы подбора; на категорию не влияет | п. 3.2, 5.3 |
| Неподтверждённый грейд — показывать со статусом и опускать, не скрывать | Кандидат с заявленным, но не подтверждённым грейдом виден в категории заявленного грейда со статусом «грейд не подтверждён тестом», **после всех подтверждённых**; L = 0, оценка × 0.6; фильтр «только подтверждённые»; отдельный счётчик на карте категорий | п. 3.3, `matching/service.py` |
| Кандидат сам выбирает грейд; подсказка по резюме допустима | Грейд выбирается в опросе; рядом подсказка по стажу (в том числе распознанному из резюме) — только ориентир | экран «Категория и тестирование» |
| Повышение — лучше отдельным тестом, не автопрыжок | После уверенного прохождения кандидату предлагается **отдельный тест на грейд выше** — сразу, без ожидания 90 дней и вне лимита попыток. Автоматического повышения нет | п. 2.4, `POST /attempts/{id}/upgrade` |
| Нельзя скакать по грейдам; провал и уход ниже — без сжигания попытки | Смена грейда — раз в 90 дней и на одну ступень; повтор того же уровня — через 14 дней. Шаг вниз после неудачи **не расходует попытку** и не запускает 90-дневную блокировку | п. 2.4, `tests/test_grade_rules.py` |
| Одинаковые задачи не должны расходиться между кандидатами | 226 семейств-генераторов: у каждого кандидата свои данные и ответ; **сервер не выдаёт уже показанный кому-либо вариант**; контроль экспозиции. Атака утечкой: из утечки 0% заданий, Junior проходит Middle в 5% (без утечки — 7%, у статичного банка — 97%) | п. 2.1, 2.5, 4 |
| Задания нейросетью допустимы, но нужны уникальность и мало ошибок | LLM не используются: ответ вычисляет генератор, и все 918 проверенных вариантов с кодом **исполнены настоящими компиляторами 9 языков и SQLite — расхождений нет** | п. 2.1, `validation/code_exec.py` |
| Песочница, прокторинг, антиплагиат, защита от LLM — плюс | Таймер на каждое задание, учёт уходов со вкладки и вставок, запрет копирования кода, person-fit (индекс lz); при сигналах грейд подтверждается **контрольной формой** из свежих заданий; уникальные варианты (готовый ответ «из интернета» не подходит). Ограничение живой подсказки без прокторинга описано честно | п. 2.6 |
| Задания от работодателя — плюс; эталон проверяет система, открытый ответ — работодатель | Регулярные задачи: автоматическая предварительная оценка по скрытой рубрике и итоговая оценка работодателя | п. 2.8 |
| Несколько категорий у кандидата — плюс | Основная категория и **до двух дополнительных**, грейд в каждой — только тестом; работодатель находит кандидата во всех категориях. Справочник — 8 специализаций в 5 направлениях | п. 3.2 |

## 11.2. ФСП и ФСП ID

| Решение на сессии | Как в «Драфте» | Где |
|---|---|---|
| Подтверждённый профиль — данные из ФСП ID, а не самозаявленный опыт | Результаты приходят из реестра по ФСП ID, подписаны; модерация не нужна | п. 5 |
| Реестр правдоподобный: места, разряды, дисциплины, командные результаты | Мок-реестр с дисциплинами, уровнями, местами, командами, ролями, стеком решения, разрядом | п. 5.3 |
| Keycloak не поднимать, вход имитировать; альтернатива — регистрация по e-mail | `fsp-mock` — OIDC с URL и токенами Keycloak (Authorization Code + PKCE, JWKS); вход и регистрация по e-mail тоже есть | п. 5.1–5.2 |
| Все соревнования равно важны, рейтинг турниров не нужен | Уровень соревнования **в оценку не входит**, рейтинга дисциплин нет. По идее из письменных ответов учитывается только актуальность дисциплины для специализации (п. 11.6) | п. 5.3 |
| Учитывать число соревнований и результативность, чтобы профиль нельзя было набить онлайн-явками | Каждый призовой и финальный результат добавляет вклад; участия без результата — с потолком 0.6, то есть меньше одного призового места | `fsp/scoring.py`, п. 5.3 |
| Срок давности — по желанию | Вклад результата убывает вдвое за 2 года | п. 5.3 |
| Корректная работа без истории ФСП | F = 0: ни штрафа, ни бонуса, кандидат в выдаче; пометка для работодателя | п. 5.4 |

## 11.3. Подбор и выход на контакт

| Решение на сессии | Как в «Драфте» | Где |
|---|---|---|
| Минимум: категоризация, объяснимый подбор, адресное приглашение; оригинальность — плюс | Потребность текстом → рекомендованные категории → подборка с «почему в подборке» → приглашение с вилкой. Дополнительно: вероятность принятия, уточнение без потери подборки, тест под вакансию, вакансии и отклики | п. 3 |
| Импорт чужих вакансий не нужен | Не делается: только вакансии и потребности работодателей платформы | — |
| Контакты открываются пригласившему после принятия; отзыв доступа — плюс | После принятия контакты видит только пригласивший работодатель. Кандидат может **закрыть доступ** в любой момент: контакты исчезают из кабинета, API и ATS-выгрузки; действие пишется в аудит | `POST /candidate/invitations/{id}/contacts` |
| Чат на платформе — плюс | **Переписка внутри принятого приглашения**: без обмена контактами, с отметкой о прочтении и уведомлениями; продолжает работать и после отзыва контактов | `GET/POST …/invitations/{id}/messages` |
| Зарплата: gross или net — подписать | Все суммы — в месяц, **до вычета НДФЛ (gross)**; подпись у каждой суммы в интерфейсе, письмах и API. Вилку «на руки» из текста вакансии разбор переводит в gross | п. 3.2 |
| Проверка компании — добровольная метка доверия, не блокирует сценарий | Индекс доверия (ИНН, домен почты, жалобы, полнота профиля) виден кандидату; влияет только на суточный лимит приглашений | п. 1.1, `services/trust.py` |

## 11.6. Письменные ответы организаторов

После сессии организаторы письменно ответили на вопросы команд трека. Ниже — каждый ответ и как он отражён в «Драфте».

| Вопрос → ответ организаторов | Как в «Драфте» | Где |
|---|---|---|
| ФСП — буст внутри подтверждённого грейда, не замена теста? → **Да.** Все дисциплины одинаково приоритетны; можно учитывать актуальность направления (ИБ-специалист с соревнованием по ИБ релевантнее, чем с робототехникой) — на усмотрение команды | ФСП двигает кандидата только внутри категории, грейд — только тестом. **Реализована идея актуальности**: вклад результата × 1.0 (профильная дисциплина), 0.8 (смежная), 0.6 (непрофильная); если стек решения совпал с навыками запроса — профильная. Рейтинга дисциплин нет, любой результат засчитывается; в объяснении выдачи написано, профильная ли дисциплина | п. 5.3, `fsp/scoring.py`, `catalog.discipline_fit` |
| Регулярные задания: адресно или челлендж? Кто оценивает? → **Адресно** (челлендж не запрещён), способ оценки — на усмотрение команды | Адресно: раз в 7 дней задача работодателя категории, с распределением нагрузки между задачами. Оценка: автопроверка по скрытой рубрике → **проверка на списывание** (почти совпадающие ответы на ту же задачу помечаются) → итоговая оценка работодателя 1–5, байесовское среднее | п. 2.8 |
| Питч, видео вместо стенда, срок стенда → **10 минут; видео допустимо; стенд держать на время оценки** | Демо-видео записывается одной командой по актуальному интерфейсу; стенд разворачивается одной командой и переподнимается без потери данных | `docs/demo_video.py`, п. 8 |
| Стабильность грейда при повторном прохождении → **процедуру предлагает команда: test–retest и разделяющая сила заданий, симуляция на синтетике допустима** | 1200 виртуальных кандидатов проходят тест дважды на разных формах: корреляция θ̂ 0.88, взвешенная κ 0.85, грейды двух прохождений расходятся не больше чем на ступень — 100%; точность грейда относительно истины — 81%, вдали от порога — 90%. Разделяющая сила: AUC соседних грейдов 0.92–0.94, медианная точечно-бисериальная корреляция 0.53. Жюри повторяет это вручную в режиме эксперта | п. 4.2, README |
| Грейд — стаж или навыки? → **Уровень навыков, подтверждённый тестом**; стаж — атрибут профиля | Грейд присваивает только тест; стаж хранится в профиле и служит подсказкой при выборе грейда | п. 3.2 |
| Несколько категорий у кандидата? → **Не обязательно, будет плюсом** | Основная + до двух дополнительных категорий, у каждой свой грейд, тест, блокировка и паузы; дополнительную можно сделать основной, чтобы пройти по ней тест; работодатель находит кандидата во всех категориях | п. 3.2, `services/categories.py` |
| Облачные LLM? → **Допустимы, в том числе зарубежные; лучше открытые модели; риски 152-ФЗ — на команде** | LLM не используются: персональные данные не покидают платформу. Если понадобятся — открытая модель у оператора платформы и только обезличенный профиль | п. 1.5 |
| Что видит работодатель до принятия? → **ФИО и места работы можно, закрыты только контакты** | Контакты закрыты до принятия. Имя и текущее место работы кандидат открывает сам: по умолчанию — код кандидата и опыт без текущей компании (слепой отбор, минимизация ПДн) | п. 3.6 |
| Тест единый под категорию или под вакансию? → **Единый под категорию, но не одинаковый пул для всех; задания под вакансию — необязательный блок регулярных заданий** | Тест по категории; у каждого кандидата свои задания (226 семейств-генераторов, адаптивный отбор, сервер не выдаёт уже показанный вариант). Задачи под вакансию — блок регулярных заданий работодателя | п. 2.1, 2.5, 2.8 |
| Ограничения по ресурсам? → **Нет, расход должен быть оправдан** | ≈ 1 ГБ RAM под нагрузкой, без GPU и внешних API | п. 1.5 |
| Скорость или качество подбора? → **Качество (35% против 7%)** | Веса подобраны на отдельных наборах, качество измерено на независимых (nDCG@10 0.79, P@5 0.85); при этом 50 одновременных пользователей — p95 ≤ 0,30 с | п. 3.3, 4.3 |
| Категория — «специализация + грейд» или детальнее? → **Достаточно специализации и грейда, детальнее — плюс** | Категория = специализация × грейд; дополнительно учитываются трек (язык, фреймворк), стек, роль в команде, отрасль и формат работы | п. 3.2 |
| Насколько жёстко подтверждать грейд, нужна ли проверка на списывание? → **Грейд выбирает кандидат, без теста — статус «не подтверждён»; официально — только по тесту. Проверка на списывание не обязательна, но большой плюс** | Неподтверждённый грейд виден со статусом и ниже подтверждённых. Против списывания: уникальные варианты, таймер на задание, уходы со вкладки и вставки, person-fit, контрольная форма при сигналах; проверка на списывание в регулярных заданиях | п. 2.5, 2.6, 2.8 |
| Что такое ATS-интеграция? → **Синхронизация вакансий, откликов и статусов с системой найма работодателя через API; в MVP — концепция (7%)** | Сквозной контур работает: вакансии из ATS по `external_id` с разбором текста, отклики и принявшие приглашение — в ATS, статусы и этапы — в обе стороны (API по ключу + подписанные вебхуки) | п. 10.2 |
| Источники данных? → **Собственные (синтетика или открытые источники); парсинг — только для тестовых данных, не как продуктовая механика** | Синтетическая популяция со скрытой истиной и мок-реестр ФСП; чужие вакансии не собираются и не показываются | п. 4.1, 5 |
| Минимальный охват? → **Двух специализаций с двумя грейдами достаточно, важен сквозной путь от теста до приглашения** | 8 специализаций × 4 грейда; сквозной путь «опрос → тест → категория → подборка → приглашение → контакты» проверен автотестами и браузерными сценариями | README, `tests/`, `frontend/e2e` |
| Дизайнеры? → **Могут быть в справочнике, приоритет — ИТ-роли; идея объективной проверки дизайнеров — плюс** | В MVP — ИТ-роли. Описана механика объективной проверки дизайнеров тем же движком: контраст WCAG, сетка и отступы, типографическая шкала, цветовые модели, законы Фиттса и Хика, эвристики Нильсена; неформализуемое — регулярной задачей с рубрикой | п. 10.4 |
