# 10. Антифрод, интеграция с ATS и развитие после MVP

## 10.1. Защита от фиктивных вакансий и недобросовестных работодателей

### Реализовано в прототипе

| Механизм | Как работает |
|---|---|
| **Индекс доверия компании** (0–100) | база 40; +15 корпоративная почта на домене сайта; +10 ИНН прошёл проверку контрольной суммы; +10 заполненный профиль; до +10 за возраст аккаунта; ±10 доля принятых приглашений; −15 за каждую открытую жалобу; −10 за вакансии с флагами риска. Факторы видны работодателю, индекс — кандидату в каждом приглашении |
| **Лимиты приглашений** | в сутки: 15 (низкое доверие) / 40 (среднее) / 120 (высокое) — массовая рассылка без репутации невозможна |
| **Флаги риска текста** | предоплата и «оплата обучения», финансовые схемы, запрос паспортных и платёжных данных, «доход без опыта», перевод общения в сторонние каналы, слишком короткое описание. Критичные флаги блокируют публикацию вакансии и отправку приглашения (`422 risky_content`), остальные показываются кандидату предупреждением |
| **Реалистичность вилки** | сравнение с рыночной медианой категории: «втрое выше рынка» — флаг риска; «заметно ниже рынка» — подсказка работодателю |
| **Жалобы кандидатов** | «Пожаловаться» в приглашении: причина + комментарий; жалоба сразу снижает индекс доверия, очередь модерации у администратора |
| **Аналитика отказов** | работодатель видит, почему ему отказывают; систематически заниженные вилки видны и платформе |

### Концепция развития

1. **Верификация юрлица**: ИНН/ОГРН по ЕГРЮЛ (API ФНС / DaData) — статус «действующее», совпадение названия и руководителя; вход через **Госуслуги для юрлиц (ЕСИА)**; подтверждение домена (DNS TXT или письмо на admin@домен).
2. **Модерация с приоритетом риска**: вакансии и первые приглашения новых компаний — в очередь; ML-модель риска (текстовые признаки, вилка, поведение аккаунта) определяет, что проверять вручную.
3. **Поведенческие сигналы**: доля приглашений без последующего контакта, «призрачные» вакансии без откликов и движения, всплески рассылок, повторяющиеся тексты у разных компаний.
4. **Репутация от кандидатов**: короткая оценка после принятия приглашения («условия совпали с обещанными?»), публичный рейтинг ответственности работодателя.
5. **Санкции**: понижение лимитов → скрытие приглашений до модерации → блокировка; апелляция.

## 10.2. Интеграция с ATS работодателя

Организаторы определили ATS-интеграцию как синхронизацию **вакансий, откликов и статусов** с внутренней системой найма
работодателя через API, чтобы платформа встраивалась в существующий процесс без ручного дублирования. В MVP это не
обязательно; в «Драфте» сквозной контур уже работает.

### Реализовано

| Что синхронизируется | Направление | Как |
|---|---|---|
| Вакансии | ATS → платформа | `PUT /ats/v1/vacancies/{external_id}` — создание или обновление по идентификатору ATS (повтор не создаёт копию). Специализацию, грейд, навыки и формат, если их нет в запросе, распознаёт тот же разбор текста, что и у потребностей; без уверенно распознанной специализации — ошибка 422, а не угаданная категория. Антифрод-проверка текста — как у ручной публикации. `GET /ats/v1/vacancies` — вакансии с `external_id` |
| Отклики | платформа → ATS | `GET /ats/v1/applications?since=…` — отклики с контактами и `external_id` вакансии; вебхук `application.created` |
| Кандидаты из приглашений | платформа → ATS | `GET /ats/v1/candidates` — принявшие приглашение, с категорией, подтверждёнными навыками и ФСП; вебхук `invitation.accepted` (отзыв контактов кандидатом убирает их из выгрузки) |
| Статусы откликов | обе стороны | из ATS — `PUT /ats/v1/applications/{id}/status` (кандидат получает уведомление); с платформы — вебхук `application.status_changed` |
| Этапы найма по приглашению | обе стороны | из ATS — `PUT /ats/v1/invitations/{id}/stage`; с платформы — вебхук `invitation.stage_changed` |

* Вебхуки подписаны `X-Draft-Signature: sha256=HMAC(secret, body)`, событие — в `X-Draft-Event`, 3 попытки с экспоненциальной
  задержкой, журнал доставки. События: `invitation.accepted`, `invitation.declined`, `invitation.stage_changed`,
  `application.created`, `application.status_changed`, `task.submitted`.
* Управление ключами и вебхуками — в кабинете («Интеграции (ATS)»); ключи хранятся хешем, отзываются в один клик.

### Концепция

* Готовые коннекторы к российским ATS (Huntflow, Potok, Talantix, E-Staff, Skillaz) поверх API выше: маппинг их моделей
  (вакансия ↔ `external_id`, этапы воронки ↔ `stage`/`status`), периодическая сверка на случай потерянного вебхука.
* Экспорт кандидата в стандартизированный JSON (JSON Resume + блок `verification`: категория, θ-перцентиль, подтверждённые
  навыки, ссылки на подписанные записи реестра ФСП) и PDF-профиль с QR-проверкой.
* OAuth 2.0 client credentials для ATS вместо статических ключей, скоупы `candidates:read`, `invitations:write`.

## 10.3. Развитие механик

| Направление | Что делаем |
|---|---|
| Тестирование | калибровка на реальных прохождениях (MML), анализ DIF между языковыми треками, **задания с исполнением кода** в песочнице (интеграция с проверяющими системами соревнований ФСП), расширение банка до 500+ семейств, прокторинг для подозрительных попыток, тесты для Lead-ролей (архитектурные кейсы с экспертной оценкой по рубрике) |
| Подбор | обучение весов ранжирования на исходах приглашений (learning to rank: принято / собеседование / найм), учёт истории отказов кандидата, «похожие кандидаты», уведомление работодателя о новых кандидатах в сохранённой подборке |
| Кандидатам | персональный план развития по слабым компетенциям, рекомендации соревнований ФСП, «рыночная стоимость» категории |
| ФСП | событийная синхронизация реестра, отображение командных ролей и вклада, бейджи ФСП в профиле, совместные задачи от партнёров ФСП как регулярные задания |

## 10.4. Дизайнеры: как тестировать объективно

Организаторы допускают дизайнеров в справочнике специализаций, но приоритет — профильные ИТ-специалисты, у которых
тестирование объективнее. Поэтому в MVP дизайнеров нет, а механика для них уже понятна и укладывается в тот же движок:

| Компетенция | Задание с однозначным ответом (генерируется заново для каждого кандидата) |
|---|---|
| Доступность | контраст пары цветов по WCAG 2.2 (выдержит ли AA/AAA для текста этого кегля), минимальный размер области нажатия, порядок фокуса |
| Сетка и вёрстка | ширина колонки 12-колоночной сетки при заданных полях и гаттерах, кратность отступов шагу 4/8 pt, пересчёт макета под брейкпоинт |
| Типографика | размер ступени модульной шкалы, межстрочный интервал по ритму, длина строки в знаках |
| Цвет | перевод HEX ↔ RGB ↔ HSL, подбор оттенка с заданным контрастом к фону |
| UX-закономерности | закон Фиттса и Хика (какой вариант быстрее), эвристики Нильсена — какая нарушена на показанном экране |
| Продуктовые метрики | конверсия воронки, значимость A/B-теста макетов |

Неформализуемая часть — композиция, вкус, работа с исследованием — проверяется **регулярной задачей с рубрикой**:
работодатель или эксперт ФСП оценивает решение по заранее заданным пунктам, а автоматическая предварительная оценка и проверка
на списывание работают так же, как у разработчиков (п. 2.8). Портфолио — самоописание, оно на грейд не влияет.

## 10.5. Технический долг и масштабирование

* Миграции схемы через Alembic (сейчас схема создаётся из метаданных SQLAlchemy при старте — идемпотентно).
* Очередь задач (Redis + RQ/Celery или Kafka) для вебхуков, писем, пересчёта подборок и синхронизации ФСП.
* Кэш справочников и банка в Redis; read-реплики PostgreSQL для поиска; выделение сервисов тестирования и подбора при росте нагрузки.
* Наблюдаемость: метрики Prometheus (RPS, латентность подборки, экспозиция семейств), трассировка, алерты по SLO.
