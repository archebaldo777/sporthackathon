# 2. Механика тестирования кандидатов

Требования ТЗ: категория кандидата определяется обязательным путём — опрос, самостоятельный выбор грейда и тест на
заявленный грейд; единый набор заданий не годится (утекает), генерация уникальных заданий нейросетью не гарантирует
сопоставимой сложности и объективности. Нужен подход, устойчивый к обеим проблемам.

**Решение «Драфта»: банк шаблонов-генераторов + теория ответов на задания (IRT) + адаптивный тест (CAT).**

| Проблема | Как решается |
|---|---|
| Задания и ответы расходятся по рынку | В банке хранятся не задания, а **семейства-генераторы**. Каждый кандидат получает свои варианты: другие данные, код, таблицы, наборы утверждений, порядок ответов. **Ответ не хранится, а вычисляется** генератором (исполнением SQL, симуляцией алгоритма, пересчётом формулы) |
| Уникальные задания несопоставимы по сложности | Варианты семейства **изоморфны** — та же когнитивная операция с другими данными. Параметры трудности калибруются на уровне семейства (IRT 3PL), итоговая оценка — на общей шкале θ |
| Нужна объективная оценка разных кандидатов | Все кандидаты специализации измеряются на одной шкале способности θ; решение о грейде — по вероятности превышения порога, а не по «проценту верных» |
| Тест должен быть коротким | Адаптивный выбор: каждое следующее задание максимально информативно около текущей оценки, тест заканчивается, когда решение о грейде надёжно → в среднем ~15 заданий (8–22) вместо 30–40 фиксированных |

## 2.1. Банк шаблонов-генераторов

226 семейств (148 параметрических генераторов и 78 комбинаторных пулов) для 8 специализаций и 26 компетенций,
4 уровня трудности (стажёр — senior). Форматы: ввод ответа (118), одиночный выбор (56), множественный выбор (52).

### Три способа порождать варианты

1. **Параметрическая генерация с вычисляемым ответом** (большинство): данные генерируются случайно, ответ вычисляется кодом.
   * SQL: случайные таблицы (`employees`, `orders`, `customers` с NULL), запрос с JOIN / GROUP BY / оконной функцией;
     эталонный ответ — **результат исполнения запроса во встроенной SQLite**.
   * Алгоритмы: случайный граф → порядок BFS/DFS; ключи → индекс в хеш-таблице с пробированием; массив → состояние после
     прохода пузырька; сетка с препятствиями → число путей (ДП); рюкзак; Дейкстра; LRU-промахи.
   * Трассировка кода: сгенерированная программа → что она выведет (с учётом семантики языка).
   * Расчётные задачи: precision/recall/F1/ROC-AUC по сгенерированным данным, шаг градиентного спуска, энтропия/Джини, k-means,
     z-тест A/B, перцентили, retention и воронки, бюджет ошибок SLO, HPA Kubernetes, CIDR и разбиение подсетей, правила
     межсетевого экрана, flex-grow, em/rem, специфичность CSS, порядок event loop JS/Dart, React state updates, Diffie–Hellman, RSA, XOR, энтропия пароля.
2. **Комбинаторные пулы утверждений** для понятийных знаний: из пула верных и неверных фактов собирается набор
   («отметьте все верные»); число комбинаций растёт комбинаторно — «заучить ответ» можно, только выучив предмет.
3. **Одна структура — 9 языков.** Универсальные семейства (циклы, рекурсия, словари, целочисленное деление, ссылочная
   семантика, try/finally) рендерятся в синтаксис языка кандидата: Python, JavaScript/TypeScript, Java, Go, C#, Kotlin, PHP,
   Swift, Dart. Ответ вычисляется **с учётом семантики языка**: `-17 // 5` в Python = −4, а `-17 / 5` в Java = −3; `%` в Dart —
   евклидов остаток; массивы в Swift и PHP копируются при присваивании, в Java/JS/Python — нет. Плюс языковые «ловушки»:
   event loop и `var/let` в JS, Integer cache в Java, `defer` и `append` в Go, отложенный LINQ в C#, `foreach` по ссылке в PHP.

Пример: семейство `sql.left_join` у двух кандидатов (фрагменты):

| Кандидат А | Кандидат Б |
|---|---|
| `customers`: 6 строк (Москва, Казань…), `orders`: 8 строк | `customers`: 5 строк, `orders`: 9 строк |
| `SELECT COUNT(*) FROM customers c LEFT JOIN orders o … WHERE o.id IS NULL;` → **1** | тот же запрос по другим данным → **2** |

Ключ ответа хранится только на сервере (`test_items.answer_key`) и никогда не отправляется клиенту.

### Ключи ответов проверены исполнением

## 2.2. Модель IRT (3PL)

Вероятность верного ответа кандидата со способностью θ на задание семейства:

```
P(θ) = c + (1 − c) / (1 + exp(−a · (θ − b)))
```

* **b — трудность**: номинальный уровень семейства → b: стажёр −1.6, junior −0.5, middle +0.55, senior +1.55 (плюс поправка семейства);
* **a — дискриминативность**: априорно по формату — ввод ответа 1.8, множественный выбор 1.6, одиночный 1.3 (для пулов −0.1);
* **c — угадывание**: одиночный выбор 0.2, множественный 0.05, ввод 0.02.

Априорные значения уточняются **онлайн-калибровкой** (п. 2.6). Шкала грейдов (пороги θ): стажёр ≥ −2, junior ≥ −1, middle ≥ 0, senior ≥ +1.

## 2.3. Адаптивный алгоритм (CAT)

1. **Старт**: θ̂₀ — центр заявленного грейда (априорное N(центр, 1)).
2. **Выбор задания**:
   * *контентная балансировка* — берётся компетенция с наибольшим дефицитом относительно плана теста;
   * среди семейств этой компетенции (подходящих языку/фреймворку кандидата, не показанных в попытке и, по возможности,
     в прошлых попытках кандидата) считается информация Фишера I(θ̂); если θ̂ ближе 0.4 к порогу грейда — в точке
     порога: решение «выше/ниже» сильнее всего уточняют задания, трудность которых совпадает с границей;
   * *контроль экспозиции (randomesque)*: случайный выбор из топ-4 по информации с весом, уменьшающимся для семейств, которые
     показываются чаще целевых 25% попыток;
   * из семейства генерируется новый вариант (зерно = хеш(seed попытки, позиция)).
3. **Оценка** после каждого ответа — EAP (апостериорное среднее на сетке из 161 точки): устойчива при малом числе ответов.
4. **Остановка — классификационная**: не меньше 8 заданий и каждая компетенция плана затронута (до 14-го задания);
   стоп, как только по **каждому** порогу грейда апостериорная вероятность «выше» или «ниже» достигла 85%. Если решение
   спорное, тест продолжается — до 22 заданий. Очевидные случаи завершаются за 8–12 заданий, пограничные получают
   больше. По Монте-Карло это правило точнее прежнего «стоп при SE ≤ 0.35» (точный грейд 83% против 81%, повтор даёт
   тот же грейд в 75% против 73%) и при этом короче в среднем (14.6 против 15.4 задания) — см. раздел 4.2.
5. **Итог**: θ̂ пересчитывается с *популяционным* априорным N(0, 1.2) — заявленный грейд не влияет на решение.

Время: на каждое задание свой лимит (90–270 с) по серверным часам, на попытку — 90 минут (типичная попытка — 35–45 минут).

## 2.4. Решение о грейде и правила пересдачи

| Ситуация | Правило |
|---|---|
| Грейд подтверждён | P(θ ≥ порог заявленного грейда) ≥ 0.5 |
| «Справился уверенно» | P(θ ≥ порог следующего грейда) ≥ 0.8 → кандидату предлагается **отдельный тест на грейд выше** — сразу, без ожидания 90 дней и вне лимита попыток (действует 14 дней, один раз). **Автоматического повышения нет**: грейд меняется, только если пройден этот тест |
| Не подтвердил | **Грейд не понижается принудительно.** Система подсказывает уровень, который тест подтверждает (наибольший с P ≥ 0.5); тест на уровень ниже доступен **сразу** |
| Сработали сигналы нечестности | грейд не присваивается до **контрольной формы** (6–10 свежих заданий, строже таймер), доступной сразу и вне лимита (п. 2.6) |
| Шаг вниз после неудачи | **не расходует попытку** из лимита и не запускает 90-дневную блокировку: подтвердив уровень ниже, кандидат может повторить неудавшийся уровень через обычные 14 дней |
| Повтор того же или более высокого уровня после неудачи | через 14 дней |
| Смена подтверждённого грейда | не чаще одного раза в **90 дней**, на одну ступень за раз |
| Лимит | не более 4 попыток за 30 дней (шаг вниз и тест на повышение по предложению не считаются) |
| Смена специализации | только после окончания блокировки; категория сбрасывается до нового теста |

**Обоснование.** Грейд присваивает только тест по категории; ни вакансия, ни достижения ФСП, ни резюме грейд не меняют
(резюме даёт лишь подсказку при выборе). Кандидат сам выбирает грейд, тест его подтверждает или нет. Скакать по грейдам
нельзя: смена — раз в 90 дней и на одну ступень. Но честная неудача не наказывается: шаг вниз бесплатен и не блокирует
повторную попытку, а сильному кандидату не нужно ждать 90 дней — он сразу получает отдельный тест на уровень выше.

Все интервалы задаются переменными окружения (`GRADE_CHANGE_COOLDOWN_DAYS`, `RETAKE_SAME_GRADE_COOLDOWN_DAYS`, `MAX_ATTEMPTS_PER_30_DAYS`).

### Профиль компетенций и подтверждённые навыки

По каждой компетенции считается своя оценка θ_c с **байесовским сжатием** к общему уровню (априорное N(θ̂, 0.8)) — при 2–3
заданиях оценка темы не «скачет». Результат — радар компетенций для кандидата и работодателя. Навыки компетенции
(например, «Базы данных и SQL» → SQL) считаются **подтверждёнными тестом**, если по компетенции ≥ 2 заданий и θ_c не ниже
порога грейда − 0.3. Подтверждение навыка участвует в ранжировании (п. 3).

## 2.5. Почему механика устойчива к распространению заданий

1. **Уже показанный вариант больше никому не выдаётся.** Перед выдачей сервер сверяет хеш содержания варианта (условие,
   код, таблицы и варианты ответа без учёта их порядка) со всеми выданными ранее и при совпадении генерирует новый
   (`service.fresh_variant`). Поэтому опубликованный «ответ» всегда относится к чужим данным. Даже без этой проверки
   два случайных варианта совпадают редко (0.87%, медиана доли уникальных — 91%), но для семейств с небольшим числом
   вариантов именно проверка свежести делает утечку бесполезной.
2. **Утечка «формы» теста маловероятна.** Формы двух кандидатов одной специализации пересекаются лишь на ~25% *семейств*,
   а не вариантов; при чистом выборе по максимуму информации было бы 33% и самое популярное семейство показывалось бы
   в 100% попыток (у нас — ≈ 49% при узкой популяции и 29% в смешанной).
3. **Атака проверена симуляцией**: Junior знает ответы на все варианты, показанные предыдущим 40 кандидатам. Без проверки
   свежести он отвечает «из утечки» на 9% заданий и проходит Middle в 18% случаев; в «Драфте» — **0% заданий из
   утечки и 5% прохождений**, как у Junior без всякой утечки (7%). У статичного банка с утечкой 60% ответов — 97%.
4. **Утечку «способа решения» видно по данным.** Если семейство внезапно стало легче, онлайн-калибровка показывает
   дрейф трудности, и семейство помечается к ревизии (в симуляции найдено 7 из 8 «утёкших» семейств).
5. **Выучить способ решения = выучить навык.** Знание, что `NOT IN` с `NULL` в подзапросе возвращает пустое множество,
   и есть компетенция, которую проверяет задание.

## 2.6. Контроль честности и онлайн-калибровка

* Ключи и проверка — только на сервере; время ответа — по серверным часам; превышение лимита + 20 с — ответ не засчитывается.
* Клиент фиксирует уходы со вкладки и вставки текста; сервер — подозрительно быстрые верные ответы на сложные задания.
* Индекс согласованности ответов **lz** (Drasgow, 1985) выявляет аномальные паттерны («провалил лёгкие, решил трудные»).
* **Контрольная форма.** Если попытка прошла порог, но lz < −2.5 или сработали два поведенческих сигнала, грейд не
  присваивается и профиль не меняется: кандидат подтверждает результат короткой формой (6–10 свежих заданий у порога,
  таймер строже на 30%), доступной сразу и вне лимита попыток. В симуляции у честных кандидатов это случается в 0.6%
  случаев. Честное ограничение: живую подсказку на половине заданий lz распознаёт лишь в ~5% попыток — в коротком
  адаптивном тесте мало данных; против неё нужен прокторинг (на сессии — «плюс, не обязательство»). Против **утечки**
  работает гарантия свежих вариантов (п. 2.5).
* `item_stats` копит экспозицию и долю верных. Калибровка (`POST /api/v1/admin/recalibrate`) оценивает трудность b
  методом максимального правдоподобия при известных θ попыток, сжимает к априорному значению
  `b = (n·b̂ + 20·b₀)/(n + 20)` и ставит флаг дрейфа, если b̂ < b₀ − 0.6. В симуляции ошибка трудности снижается с 0.30 до 0.19.

## 2.7. Как система формирует тест под описание вакансии

ТЗ просит показать, как по описанию вакансии формируются задания. Для потребности или вакансии
(`GET /employer/needs/{id}/test-plan`, `GET /employer/vacancies/{id}/test-plan`, кнопка «Как тестировали кандидатов»):

1. навыки вакансии нормализуются по онтологии (`postgres` → PostgreSQL) и сопоставляются компетенциям теста
   (PostgreSQL → «Базы данных», 0.85; Kafka → «Архитектура», 0.6; Docker → «Git, Docker, Linux»);
2. по навыкам определяется трек (язык, фреймворк);
3. доли базового плана специализации смещаются к покрытым компетенциям: `w'_c = w_c · (1 + 1.2 · доля навыков вакансии в c)`;
4. показываются план, число семейств на компетенцию и **примеры сгенерированных вариантов** — у каждого кандидата свои.

Навыки, которые тест не проверяет напрямую (например, Figma), учитываются через ФСП, регулярные задачи и резюме.

## 2.8. Регулярные короткие задания

Задание **адресное**, как в ТЗ: раз в 7 дней система предлагает кандидату задачу работодателя его категории (приоритет —
компании, которые сейчас ищут людей этой категории; затем — наименее загруженные задачи, чтобы одну задачу не решала вся
категория и ответы не расходились). Кандидат решает задачу или описывает подход.

Логика оценки — двухступенчатая:

1. **Автоматическая предварительная оценка** по скрытой рубрике работодателя: доля раскрытых ключевых пунктов (нечёткое
   сравнение) с поправкой на полноту ответа. Работодатель сразу видит, какие пункты не раскрыты.
2. **Проверка на списывание**: если решение почти совпадает с уже отправленным ответом другого кандидата на ту же задачу
   (сходство ≥ 90% по набору слов, порядок и мелкие правки не скрывают совпадение), работодатель видит пометку
   «возможное списывание» с кодом второго кандидата.
3. **Итоговая оценка работодателя 1–5** — именно она влияет на профиль. Байесовское среднее (одна случайная «пятёрка» не
   перевешивает) и свежесть активности входят в компоненту «Актуальность» ранжирования и в силу профиля; навыки задачи
   с оценкой ≥ 4 становятся доказательством «подтверждён задачей» (сила 0.8).

Работодатель видит автора сильного решения и может сразу его пригласить. Задания под конкретную вакансию — отдельный
необязательный блок того же механизма; на грейд регулярные задания не влияют, грейд присваивает только тест.
