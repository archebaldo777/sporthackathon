# 5. Схема интеграции с ФСП ID и реестром достижений ФСП

API и структура данных ФСП в рамках хакатона намеренно не предоставлялись. Мы спроектировали интеграцию так, чтобы
переход на настоящие сервисы ФСП требовал **только смены адресов и секретов**, а не изменения кода платформы.

## 5.1. Состав

| Компонент | В прототипе | В продакшене |
|---|---|---|
| ФСП ID | `fsp-mock`: OIDC-провайдер с URL и форматом токенов Keycloak (`/realms/fsp/protocol/openid-connect/…`), RS256, JWKS, PKCE | Keycloak ФСП (реалм `fsp`), клиент `draft-platform` (confidential) |
| Реестр достижений | `fsp-mock`: `/api/v1/athletes/{fsp_id}`, `/api/v1/athletes/{fsp_id}/results`, `/api/v1/events` | сервис реестра ФСП с тем же контрактом (предложение команды) |
| Платформа | `backend/app/fsp/client.py` — discovery, авторизация, обмен кода, проверка `id_token` по JWKS, загрузка результатов | без изменений |

## 5.2. Поток связывания профиля (Authorization Code + PKCE)

```
Кандидат (браузер)            Платформа (backend)                    ФСП ID (Keycloak)              Реестр ФСП
──────────────────            ───────────────────                    ─────────────────              ──────────
«Связать с ФСП ID» ───────▶ GET /auth/fsp/link
                             state, nonce, code_verifier → oidc_states
                             ◀── authorize_url (S256 code_challenge)
переход ─────────────────────────────────────────────────────────▶ /auth: вход, согласие на scope
                                                                     openid profile email fsp_achievements
◀───────────────────────────────────────────────────── 302 /auth/fsp/callback?code&state
POST /auth/fsp/callback ───▶ проверка state (≤ 10 мин), обмен code ─▶ /token (client_secret + code_verifier)
                             ◀──────────────────────────────────── access_token, id_token (RS256)
                             проверка подписи id_token по JWKS, iss, aud, nonce
                             users.fsp_sub = sub; candidate.fsp_id = claim fsp_id
                             GET /athletes/{fsp_id}/results (Bearer access_token) ─────────────────▶ подписанные результаты
                             сохранение fsp_achievements, расчёт fsp_score, согласие fsp_data в журнал
◀── «ФСП ID связан, получено достижений: N»
```

Тот же поток с `intent=login` позволяет **войти или зарегистрироваться через ФСП ID**: если `sub` уже связан — выдаются токены
платформы; если нет — создаётся аккаунт кандидата с подтверждённым e-mail из ФСП ID (при совпадении e-mail с существующим
аккаунтом связь не делается автоматически — защита от захвата аккаунта; пользователь входит паролем и связывает в настройках).

Фоновая синхронизация: `POST /candidate/fsp/sync` получает сервисный токен (`client_credentials`, роль `registry-reader`) и
обновляет результаты. В продакшене — по расписанию и по событию реестра (вебхук «новые результаты соревнования»).

## 5.3. Предлагаемый контракт реестра достижений

```json
GET /api/v1/athletes/FSP-2186491/results
{
  "athlete": {"fsp_id": "FSP-2186491", "full_name": "Егор Ильин", "region": "Калининградская область",
              "sport_rank": "КМС", "rating": 1834, "club": "Клуб спортивного программирования «Kernel»"},
  "results": [{
    "result_id": "R-EV-2026-021-6491",
    "event": {"event_id": "EV-2026-021", "name": "Чемпионат СЗФО по продуктовому программированию 2026",
              "discipline": "product", "level": "interregional", "start_date": "2026-03-14", "city": "Санкт-Петербург",
              "format": "team", "participants": 104},
    "place": 2, "units_total": 26, "percentile": 0.962,
    "team_name": "KernelLambda", "team_role": "Backend-разработчик",
    "score": 91.4, "stack": ["Python", "FastAPI", "PostgreSQL", "Docker"],
    "diploma_url": "https://…/R-EV-2026-021-6491.pdf",
    "signature": "<подпись записи реестром>"
  }],
  "schema_version": "1.0"
}
```

Почему именно эти поля (что полезно работодателю):

| Поле | Зачем |
|---|---|
| `discipline` (5 официальных дисциплин: алгоритмическое, продуктовое, ИБ, робототехника, БАС) | показывается работодателю; рейтинга дисциплин нет, учитывается только **актуальность дисциплины для специализации** (профильная 1.0, смежная 0.8, непрофильная 0.6) |
| `level` (региональный, межрегиональный, всероссийский, международный) | показывается работодателю; в оценку **не входит** — «чемпионат России» не весит больше хакатона |
| `place`, `units_total`, `percentile` | результативность (победитель 1.0, призёр 0.85/0.75, финалист топ-10% 0.55, топ-25% 0.4, участник 0.2) |
| `team_role`, `stack` | **подтверждение конкретных навыков**: стек решения — доказательство силы 0.9 в подборе |
| `date` | затухание давности (полупериод 2 года) |
| `signature`, `diploma_url` | проверяемость записи и диплома |
| `sport_rank`, `rating` | спортивный разряд и рейтинг ФСП в профиле |

Оценка (`app/fsp/scoring.py`):

```
вклад результата = фактор результата × давность × актуальность дисциплины
Σ = Σ вклады призовых и финальных результатов + min(Σ вклады участий без результата, 0.6)
fsp_score = 1 − exp(−Σ / 2) ∈ [0, 1]
```

Решения, согласованные с постановщиками на сессии вопросов и ответов и в письменных ответах организаторов:

* **Все соревнования и дисциплины ФСП равноценны** — внутреннего рейтинга турниров и дисциплин нет, уровень соревнования
  отображается, но в оценку не входит.
* **Актуальность дисциплины для специализации** (идея организаторов из письменных ответов: специалист по ИБ с
  соревнованием по ИБ релевантнее, чем с соревнованием по робототехнике). Это не рейтинг дисциплин, а соответствие
  дисциплины профессии: результат в профильной дисциплине учитывается полностью, в смежной — с весом 0.8,
  в непрофильной — 0.6 (любой результат ФСП засчитывается). Если стек решения совпал с навыками запроса работодателя,
  результат считается профильным независимо от дисциплины. В профиле актуальность считается к специализации кандидата,
  в подборке — к специализации и навыкам запроса; в объяснении выдачи написано, профильная ли дисциплина.

| Дисциплина | Профильная для | Смежная для | Непрофильная для |
|---|---|---|---|
| Продуктовое программирование | Backend, Frontend, Mobile | ML, аналитика, DevOps, QA, ИБ | — |
| Алгоритмическое программирование | Backend, ML | Frontend, Mobile, аналитика, ИБ | DevOps, QA |
| Программирование систем ИБ | ИБ | Backend, DevOps, QA | Frontend, Mobile, ML, аналитика |
| Робототехника | — | Backend, Mobile, ML | Frontend, аналитика, DevOps, QA, ИБ |
| Беспилотные авиационные системы | — | Backend, Mobile, ML | Frontend, аналитика, DevOps, QA, ИБ |
* **Учитываются результативность и число соревнований**: каждое призовое или финальное место добавляет вклад.
* **Профиль нельзя «набить» онлайн-явками**: участия без результата суммируются с потолком 0.6 — любое их число весит
  меньше одного призового места (победитель — 1.0, призёр — 0.75–0.85).
* **Срок давности**: вклад результата убывает вдвое за 2 года — свежий результат котируется сильнее.
* **ФСП не влияет на грейд**: грейд присваивает только тест; `fsp_score` двигает кандидата внутри категории.

## 5.4. Кандидат без истории ФСП

Обязательное требование ТЗ — корректная обработка отсутствия истории:

* категория определяется **только тестом** — отсутствие ФСП на неё не влияет;
* в ранжировании компонента F = 0: участники ФСП получают бонус, но кандидат без истории **не штрафуется и не исключается**
  (проверено автотестом `test_candidate_without_fsp_handled` и в валидации);
* в карточке работодателя — пояснение «Кандидат пока не участвовал в соревнованиях ФСП или не связал ФСП ID — это не влияет на категорию»;
* кандидату — мягкое предложение связать ФСП ID; если ФСП ID связан, но результатов нет, — отдельное сообщение.

## 5.5. Переход на настоящий ФСП ID (Keycloak)

1. В реалме ФСП создать confidential-клиент `draft-platform`: Standard Flow + PKCE (S256), Valid Redirect URI
   `https://<домен платформы>/auth/fsp/callback`, Service Accounts (для синхронизации).
2. Добавить client scope `fsp_achievements` и protocol mapper атрибута пользователя `fsp_id` в access и id token.
3. Реестру достижений проверять токены Keycloak (audience `fsp-registry`) и отдавать данные только владельцу (`fsp_id` из
   токена) или сервисному аккаунту с ролью `registry-reader`.
4. На платформе задать переменные:

```
FSP_OIDC_PUBLIC_BASE=https://id.fsp-russia.ru        # адрес Keycloak для браузера
FSP_OIDC_INTERNAL_BASE=https://id.fsp-russia.ru      # адрес для backend (может совпадать)
FSP_REALM=fsp
FSP_CLIENT_ID=draft-platform
FSP_CLIENT_SECRET=<секрет клиента>
FSP_REGISTRY_API=https://registry.fsp-russia.ru/api/v1
```

Платформа использует стандартный discovery (`/.well-known/openid-configuration`), поэтому других изменений не требуется.

### Совместимость собственных токенов платформы

Access-токены платформы подписываются RS256 и повторяют структуру Keycloak: `iss`, `sub`, `aud`, `azp`, `typ`,
`realm_access.roles`, `email_verified`, `preferred_username`; публичный ключ доступен в формате JWKS (`/api/v1/auth/jwks`).
Поэтому при желании ФСП платформа может полностью перейти на Keycloak как единый провайдер: бизнес-код читает те же claims,
меняется только источник токена (issuer + JWKS URL).
